## D2 [2026-09-09T11:48:44Z] 采用路径级多行锁，减少无关文件互相阻塞
- **决策**：四个资源仍分别使用 `locks/code.lock`、`locks/results.lock`、`locks/discussion.lock`、`locks/files.lock`，但每一行锁记录增加路径字段：`<模式> <agent> <UTC时间戳> <路径>`。同一锁文件中可有多行，分别表示不同文件或目录的锁状态；省略路径的旧格式视为锁整个资源目录。
- **理由**：代码和结果文件增多后，目录级整锁会让无关文件互相等待；为每个文件新建一个锁文件又会让 `locks/` 难以维护。路径级多行锁在保持 `git push` 原子抢锁机制的同时，允许无重叠路径并行工作。
- **参与者**：全体已讨论同意；由 agent_B 记录并更新协议。
- **影响**：之后读写共享区时优先锁具体文件或目录，只有需要跨目录大改时才锁整个资源。判断冲突时先看路径是否重叠，再按读写锁兼容表处理。

## D3 [2026-09-09T12:14:35Z] 新增「读/写前置检查」：先同步远程，再看队友需求与 WIP
- **决策**：`rules.md` 第 1 节新增 `1.0 前置检查`——每次读/写任何共享内容前，先 ① `git pull --rebase` 看远程有无更新（新提交/新锁/新决策）；② 读 `requests/*.md`（有无 `@你` 的新需求）与 `locks/*.lock`（队友正持锁改哪个路径 = 正在做的工作 WIP）。两步确认后再按第 3 节加锁读/写。原「三条铁律」保留为 `1.1`，计数不变。
- **理由**：此前「pull 同步」散落在第 4 节、「读 requests」是第 5 节的「定期」要求，都未绑定到「每次读/写前」这一动作，也缺少「查看队友正在进行的工作」。合并为一条显式前置检查，减少因未同步或未察觉队友动态导致的撞车与漏接需求。
- **参与者**：agent_A 提出并记录（应用户要求）。
- **影响**：所有 agent 每次读/写前先做这两步；不改动三条铁律与第 3 节锁协议本身。

## D4 [2026-09-09T12:42:00Z] 新增「状态优先」硬规则：先更新并 push 状态，再写内容
- **决策**：`rules.md` 的 `1.0` 升级为「开工前置：① 查远程 → ② 查队友 → ③ 报自己状态并 push → 然后才写内容」。第 3 步为硬性要求：做任何事之前，先在自己的 `requests/agent_<你>.md`「当前状态 · 正在做」写下将做的事并 `git push`，之后才拿锁、写内容；顺序不可颠倒。纯读取时状态可从简，但写内容前必须先 push 状态。第 5 节与第 8 节两个示例已同步。
- **理由**：状态板是队友感知你意图的唯一异步渠道。若先写内容再补状态，队友的前置检查（D3 的第①②步）看不到你在干什么，易重复劳动或撞车。先报状态 = 先声明意图，与路径级锁（D2）配合进一步降低冲突。
- **参与者**：agent_A 提出并记录（应用户要求）。
- **影响**：所有 agent 每次动手前先 push 一条状态；状态板免锁，是独立的小 push；与 D3 的前置检查合并为完整「开工前置」。

## D5 [2026-09-09T13:29:01Z] 废除读锁(R)、写操作合并 push、读取免锁
- **决策**：① 取消读锁 R，锁只保留写锁 W——读取任何共享文件都不加锁，只需先查目标路径有无活跃 W 锁，有则暂缓读、无则直接读；② 写操作流程从「报状态 push → 拿锁 push → 内容 push → 释放锁 push → 状态 push」(~10 次网络往返) 压缩为 **3 次**：`pull` → (状态 + 加锁) 合并一个 commit push → 本地写 → (内容 + 解锁 + 状态) 合并一个 commit push；③ 3.4 回退升级为 `git reset --soft HEAD~1` + `git restore --staged --worktree <lockfile>` + `git pull --rebase --autostash`，因为拿锁 commit 现在同时含锁文件和状态板。rules.md 第 1/2/3/5/6/7/8 节、AGENTS.md 铁律1、4 个锁文件注释头同步更新。
- **理由**：诊断发现每次完整流程慢的根因是 ~10 次串行 GitHub 网络往返(HTTPS+GCM 单次 1.2-2.7s)，而非本地操作(本地 git <0.05s)。读锁在 git 模型下多余——git 以 commit 为原子快照，读方永远读到完整版本，不会读到“写了一半”的文件；读取真正的风险只是“读到即将被覆盖的旧版”，靠查 W 锁即可规避。合并 push 把锁的 acquire/release 并入相邻 push，往返从 10 降到 3，且不损失锁语义(push 原子性仍是串行化基础、W 锁仍独占路径、租约仍防死锁)。
- **参与者**：agent_A 提出并记录(应用户要求)；用户在两个决策点拍板(彻底废除 R 锁、立即落地)。
- **影响**：读取共享文件不再加锁、不再 push(读操作 0 往返)；写操作合并为 2 次 push。锁文件只剩 W 行，兼容表简化为“W vs W 路径重叠则等待”。**对 D4 的调整**：D4 “做任何事前先 push 状态”细化为“写操作前才 push 状态(与锁合并)，纯读取不产出内容时不 push”。D0-D4 的核心(单一 owner 免锁、push 原子性、路径级锁 D2、前置检查 D3、状态优先 D4)均保留，本条是其上的效率优化。旧的 R 锁行若残留视为无效，可忽略或顺手清理。
