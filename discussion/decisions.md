## 正式阶段 · 决策记录（D9 起）

## D9 [2026-09-10T17:05:19Z] 通信层闭环改「发起方追踪制」+ 请求区活跃/归档分离

**决策**：
1. **请求区拆两段**：`requests/agent_<你>.md` 的「我发出的请求」分为 `活跃（待认领/进行中/待复核）` 与 `已闭环·归档` 两段——活跃段置顶只留未闭环项，归档段每条压成一行（时间 + @谁 + 事 + 结果 commit），详情靠 git 历史追溯。
2. **闭环责任 = 发起方追踪制**：谁发请求谁负责闭环。发起方主动查对方的提交/结果、自行核验并更新状态，核验通过即把该条移入归档段；**不再依赖被请求方回报**（异步协作中对方常不回报）。
3. **「认领/回报」降级为自愿加分项**：被请求方可在自己板登记认领、完成后回报（或直接在「最近完成」末尾带 `(@发起agent 已闭环)`）；填了帮发起方省事，不填也不影响闭环。

**理由**：原协议（docs 2.5）设计「发起→认领→回报」双向闭环，但被请求方（尤其 codex 类 agent）常只写「最近完成」、不填「认领/回报」，导致闭环断裂、发起方无从追踪（实例：agent_A 发的多条请求，B/C 实际完成却从未回报，A 只能主动翻对方提交核验）；且「发出请求」区把已完成/待认领/待复核混堆、越积越长，难一眼看清未闭环项。改为发起方单方追踪 + 活跃/归档分离，既降低对对方配合的依赖，又提升可读性。

**参与者**：agent_A（提出，本机用户确认方向）。

**影响**：改 `rules.md` 第 2 层速览 + `docs/2-communication.md` 2.3/2.5；三个 agent 板子结构建议按新格式重构（agent_A 先行示范）；B/C 下次读本协议后遵循（回报转为自愿）。向后兼容：旧板已完成的请求可逐步迁入归档段。
