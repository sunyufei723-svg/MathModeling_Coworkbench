# 第 2 层 · 通信层详解（requests/）

> 展开 `rules.md`「第 2 层 通信层」：状态板结构、单一 owner 免锁、状态优先、@请求 / 认领 / 回报。
> 简洁规则见 [`rules.md`](../rules.md)。

---

## 2.1 作用

`requests/` 是 agent 之间**唯一的异步通信渠道**：广播自己要做什么、向别人发请求、认领任务、回报进度。每个 agent 一个文件：`requests/agent_A.md` / `agent_B.md` / `agent_C.md`。

## 2.2 单一 owner = 免锁

- **只有你本人写自己的** `requests/agent_<你>.md`，别人只读。
- 因此请求区**不需要加锁**、天然无冲突（这也是它永不与人冲突、可作回退兜底的原因，见 `docs/5-concurrency.md` 5.7）。
- 要回应别人，在**你自己的**文件里写，**绝不去改对方的文件**。

## 2.3 状态板结构（`requests/agent_<你>.md`）

```
## 我是谁 / 负责方向
## 当前状态
- 正在做：<将做/正在做的事 + 目标路径>
- 持有的锁：<资源 + 路径 + 时间戳，或「无」>
- 阻塞 / 等待：<在等谁、等什么，或「无」>
## 我发出的请求 · 活跃（待认领 / 进行中 / 待复核）
## 我发出的请求 · 已闭环（归档：一行一条，详情见 git 历史）
## 我认领的任务（来自他人请求 · 自愿）
## 完成回报（通知发起方 · 自愿；或直接在「最近完成」尾带 @发起agent 已闭环）
```

## 2.4 状态优先（硬性顺序，最重要）

- 写任何共享内容**之前**，先把「你要做什么」写进「当前状态 · 正在做」，**和加锁合并成一个 commit push 出去**。
- 做完在最后一次 push 里把状态改为进度或删回「空闲」。
- **绝不允许先写内容、后补状态**——否则队友的前置检查（`git pull` 后读 requests）看不到你的意图，易重复劳动或撞车。
- 纯读取、不产出内容时**无需报状态**（0 push）。

## 2.5 请别人做事 / 追踪闭环 / 自愿回报（D9：发起方追踪制）

- **发请求**：在自己文件「发出请求 · 活跃」区追加一行 `@` 目标 agent：
  ```
  - [2026-09-09T14:30Z] @agent_B 请把 results/fig3.png 重画成 300dpi  状态:待认领
  ```
- **闭环靠发起方追踪（关键 · D9）**：谁发请求谁负责闭环。发起方定期查对方的提交/结果（`git log`、对方板「最近完成」、产物文件），自行核验并把状态从 `待认领 → 进行中 → 已复核` 更新；核验通过后，把该条从「活跃」移入「已闭环 · 归档」段、压成一行（`- [时间] @谁 事项 → 结果（commit）`，详情靠 git 历史）。**不依赖对方回报**——异步协作中对方（尤其 codex 类）常常只写「最近完成」、不回填，发起方必须主动追踪。
- **被请求方认领 / 回报（自愿加分项）**：看到 `@你` 且「待认领」的，可在**你自己的**文件登记认领与进度；完成后回报发起方——最省事的方式是直接在你「最近完成」那条末尾带 `(@发起agent 已闭环)`。**填了帮发起方省事，不填也不影响闭环**（发起方会追踪）。绝不去改对方的文件。
  ```
  - [2026-09-09T15:00Z] 重画 fig3.png 为 300dpi 完成，见 results/fig3.png (@agent_A 已闭环)
  ```
